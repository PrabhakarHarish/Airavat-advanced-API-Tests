1. FRAMEWORK OVERVIEW & ARCHITECTURAL OBJECTIVES
--------------------------------------------------------------------------------
This project is an enterprise-grade, production-ready Automated API Testing
Framework engineered specifically for the Airavat Financial Modeling & Analytics
Platform.

The Airavat Platform performs intensive quantitative financial workflows:
- Dynamic 3-statement financial modeling (Income Statement, Balance Sheet, Cash Flow).
- Complex DCF (Discounted Cash Flow), WACC, EBITDA, and Valuation calculations.
- Multi-tier recursive dependency graph formula resolutions.
- Real-time cell-level autosave synchronization and scenario branching.
- Spreadsheet parsing and generation (OpenXML / Excel .xlsx, .xlsm).
- Multi-tenant data segregation, access control, and financial reporting.

The testing framework covers 27 advanced end-to-end (E2E), mathematical precision,
concurrency, file-parser hardening, security/IDOR, and performance benchmarks.
It supports both live backend testing (against remote target environments such
as https://10.20.11.244:3000) and fully autonomous offline execution via a built-in,
high-fidelity, multi-threaded mock server engine.

--------------------------------------------------------------------------------

- Purpose:
  Master configuration file for the Pytest execution engine.

  * Registers custom test classification markers:

      - `high`: Priority 2 (P2) tests.
      - `security`: Security, Tenant Isolation, and IDOR tests.
      - `concurrency`: Concurrency, race condition, and stress tests.

2. utils/api_client.py
--------------------------------------------------------------------------------
- Location: `utils/api_client.py`
- Purpose:
  Production-grade synchronous HTTP client wrapping Python `requests.Session`.
- Key Features & Methods:
  * Persistent session handling: Preserves cookies (`sessionid`, `csrftoken`) and
    bearer authorization tokens across chained requests.
  * Allure Step Integration: Automatically wraps every request in an `allure.step`
    and logs request details (URL, method, headers, payload, status, elapsed ms).
  * Request timing: Measures execution time with `time.perf_counter()` and attaches
    `elapsed_ms` directly to response objects.
  * `_sync_csrf_headers()`: Automatically captures CSRF cookie and synchronizes
    it to the `X-CSRFToken` header.
  * Core verbs: `get()`, `post()`, `put()`, `patch()`, `delete()`.
  * Domain-specific endpoints:
      - `login(username, password)`: Handles credential submission, token storage.
      - `logout()`: Clears active credentials and session tokens.
      - `upload_excel(file_content, filename)`: Multipart file uploads.
      - `validate_pnl(template_id)`: P&L balance verification.
      - `convert_to_model(template_id, name)`: Converts uploaded file to model.
      - `get_model(model_id)`: Retrieves model metadata and cell grids.
      - `update_model(model_id, payload)`: Mutates assumptions and version.
      - `autosave_cell(model_id, cell, value, formula)`: Submits cell edit.
      - `export_excel(model_id)`: Streams exported binary workbook.
      - `duplicate_model(model_id, new_name)`: Clones/branches a model.
      - `delete_model(model_id)`: Deletes model entity.
      - `recalculate(model_id, payload)`: Triggers recalculation engine.
      - `get_preferred_profile()`: Verifies user session validity.

4. utils/assertions.py
--------------------------------------------------------------------------------
- Location: `utils/assertions.py`
- Purpose:
  Specialized assertion library for high-precision mathematical calculations,
  security headers, and vulnerability defense validation.
- Key Assertion Functions:
  * `assert_financial_precision(actual, expected, decimal_places=4, tolerance=0.0001)`:
      Uses Python's `decimal.Decimal` and `ROUND_HALF_UP` to prevent binary floating-point
      inaccuracies (e.g., IEEE-754 float drift) from causing false test failures or
      masking calculation inaccuracies.
  * `assert_security_headers(headers, is_financial_endpoint=False)`:
      Verifies presence and correctness of critical security headers:
      - `X-Content-Type-Options: nosniff`
      - `X-Frame-Options: DENY` or `SAMEORIGIN`
      - `Strict-Transport-Security` (HSTS with max-age)
      - `Cache-Control: no-store` / `no-cache` (enforced on financial endpoints).
  * `assert_no_server_leakage(headers)`:
      Verifies that `Server` and application headers do not leak framework runtime
      versions (such as specific CPython versions or internal WSGI server software).
  * `assert_no_stacktrace_in_error(response_body)`:
      Scans error responses for sensitive source code leakage, including Python
      tracebacks, database error messages, or internal file paths.
  * `assert_xss_sanitized(content)`:
      Ensures that script tags (`<script>`, `<img>`, `<svg>`) are either completely
      stripped or converted into safe HTML entities (`&lt;`, `&gt;`).
  * `assert_formula_sanitized(exported_cell_value)`:
      Ensures spreadsheet formula trigger characters (`=`, `@`, `+`, `-`) are
      disarmed (e.g., prepended with a single quote) to prevent CSV/Excel formula
      command execution attacks.

5. utils/file_generator.py
--------------------------------------------------------------------------------
- Location: `utils/file_generator.py`
- Purpose:
  Programmatic in-memory binary file generator producing valid 3-statement financial
  workbooks and weaponized/corrupted files for security and parser robustness testing.
- Key Generator Functions:
  * `create_valid_financial_workbook()`:
      Generates an in-memory `openpyxl.Workbook` containing three fully structured
      sheets: Income Statement (with Operating Revenue, Operating Expenses, and formula
      `=D16-D17`), Balance Sheet, and Cash Flow Statement. Returns an `io.BytesIO` buffer.
  * `create_corrupted_financial_workbook()`:
      Modifies a valid workbook's underlying OpenXML zip archive by replacing
      `sheet2.xml` with malformed, unclosed XML tags to test parser rollback.
  * `create_zip_bomb_xlsx()`:
      Crafts an OpenXML archive with a massive uncompressed payload (10MB+ repeating
      zero bytes) compressed into a tiny footprint to test decompression bomb defenses.
  * `create_xxe_xlsx()`:
      Injects a malicious XML DOCTYPE external entity declaration referencing
      `file:///etc/passwd` into `xl/workbook.xml` to test XML External Entity defenses.
  * `create_macro_enabled_xlsx()`:
      Injects a binary `xl/vbaProject.bin` into an `.xlsx` archive to test VBA macro
      detection, rejection, and stripping.
  * `create_formula_injection_xlsx()`:
      Generates a spreadsheet with executable command injection formulas in cells
      (`=cmd|' /C calc'!A0`, `@SUM(1+1)*cmd|...`).
  * `create_truncated_header_file()`:
      Generates a raw byte sequence containing only the 10-byte ZIP magic header
      (`PK\x03\x04...`) without payload or central directory to test corrupt stream handling.

7. MOCK SERVER DIRECTORY (`mock_server/`)
================================================================================
Purpose:
Houses a high-fidelity, in-memory, multi-threaded HTTP server emulating the entire
Airavat Platform API surface. It allows 100% of the 27 test scenarios to run
offline, in CI/CD environments, or during air-gapped security audits.

1. mock_server/__init__.py
--------------------------------------------------------------------------------
- Location: `mock_server/__init__.py`
- Purpose:
  Exports `MockAiravatServer` and `MockAiravatHandler`.

2. mock_server/airavat_mock_api.py
--------------------------------------------------------------------------------
- Location: `mock_server/airavat_mock_api.py`
- Purpose:
  Full simulation of the Airavat REST API using Python standard library `http.server`
  and `socketserver.ThreadingMixIn`.
- Detailed Capabilities & Implemented Routes:
  * `ThreadedHTTPServer`: Multi-threaded daemon server handling simultaneous connections.
  * In-Memory State:
      - `db_models`: Dict storing financial models, cell values, and versions.
      - `active_sessions` & `active_tokens`: Authentication session registries.
      - `idempotency_records`: Maps idempotency keys to created model IDs.
      - `failed_login_attempts`: Rolling timestamp buffer for rate limiting.
      - `lock`: Threading re-entrant lock (`RLock`) ensuring atomic operations.
  * Security Headers:
      Every response automatically receives `X-Content-Type-Options: nosniff`,
      `X-Frame-Options: DENY`, `Strict-Transport-Security`, and `Server: Airavat-Gateway/1.0`.
      Financial responses include `Cache-Control: no-store, no-cache`.
  * Simulated Endpoints:
      - `POST /API/login/`:
          Authenticates valid users (`analyst_alpha`, `analyst_beta`). Returns JWT token,
          session cookie, and CSRF cookie. Implements brute-force rate limiting: if > 5
          failed attempts occur within 5 seconds, returns `429 Too Many Requests` with
          `Retry-After: 5`.
      - `GET /API/logout/`:
          Invalidates tokens and cookies in the server's session registry.
      - `POST /API/get-preferred-profile`:
          Validates active authentication; rejects invalidated sessions with 401.
      - `POST /API/excel/upload/`:
          Parses multipart body. Rejects zero-byte/truncated streams with `400 Bad Request`
          (`corrupt_file_header`). Rejects zip bombs with `413 Payload Too Large`.
          Sanitizes XXE injections and returns a valid `upload_id`.
      - `POST /API/excel/validate-pnl/`:
          Returns `BALANCED` reconciliation status and `0.00` variance.
      - `POST /API/excel/convert-to-model/`:
          Converts uploaded templates to models. Rejects corrupt templates with
          `422 Unprocessable Entity` (`PARSE_ERROR`).
      - `POST /API/models/`:
          Creates models. Enforces CSRF token checking for cookie-based sessions.
          Supports `Idempotency-Key` headers to prevent duplicate creation on double-submit.
          Sanitizes model names against XSS using HTML entity encoding.
      - `GET /API/models/{id}/`:
          Retrieves model state. Enforces tenant isolation (returns 403 if Tenant B
          attempts to read Tenant A's model). Supports SQL injection query parameter testing.
      - `PUT /API/models/{id}/`:
          Updates assumptions and cells. Enforces tenant isolation. Implements
          Optimistic Locking: rejects updates with stale version numbers with `409 Conflict`.
          Simulates 4-tier formula cascade recalculations (Tier 0 -> Tier 4).
      - `DELETE /API/models/{id}/`:
          Deletes model. Enforces tenant isolation; returns `204 No Content`.
      - `POST /API/models/{id}/autosave/`:
          Saves cell edits. Implements recursive cycle detection: detects circular
          references (e.g. A1 -> B1 -> A1) and returns `400 Bad Request`
          (`CIRCULAR_DEPENDENCY_ERROR`) within SLA limits.
      - `POST /API/models/{id}/duplicate/`:
          Clones a model into an isolated child model with independent mutability.
      - `POST /API/models/{id}/recalculate/`:
          Evaluates P&L sums with 4-decimal precision, handles division by zero by
          returning `#DIV/0!` cell errors without 500 crashes, processes multi-currency
          FX consolidations, and evaluates 9,000-cell matrices under 1500ms.
      - `GET /API/models/{id}/export/excel/`:
          Generates binary `.xlsx` stream. Enforces tenant isolation and strips malicious
          VBA macros and formula command triggers.

================================================================================
9. RUNTIME, CACHE & SYSTEM DIRECTORIES
================================================================================

1. allure-results/
--------------------------------------------------------------------------------
- Purpose:
  Runtime output directory where `allure-pytest` writes raw test execution telemetry.
- Contents:
  * `*-result.json`: Individual test execution metadata (test name, status, duration,
    start/stop timestamps, test steps, severity, suite markers).
  * `*-container.json`: Test fixture setup and teardown lifecycle metadata.
  * `*-attachment.json` & `*-attachment.txt`: Captured request/response payloads,
    timing metrics, and error logs attached during test execution.
- Usage:
  Compiled into an interactive HTML dashboard using `allure generate` or `allure serve`.

2. .pytest_cache/
--------------------------------------------------------------------------------
- Purpose:
  Internal cache created by the Pytest runner to store state between executions.
- Contents:
  * `v/cache/lastfailed`: Tracks tests that failed in the previous run for `--lf` reruns.
  * `v/cache/stepwise`: Tracks resumption point when using the `--sw` flag.
  * `v/cache/nodeids`: Cached mapping of discovered test node identifiers.

3. .venv/
--------------------------------------------------------------------------------
- Purpose:
  Isolated Python 3.12 virtual environment containing installed third-party libraries
  (pytest, openpyxl, httpx, requests, allure-pytest, etc.) and executable binaries.
- Standard Sub-structure:
  * `.venv/bin/`: Contains `python`, `pip`, `pytest`, and related executable entry points.
  * `.venv/lib/python3.12/site-packages/`: Contains all installed library wheels.
  * `.venv/pyvenv.cfg`: Virtual environment configuration mapping to the system Python interpreter.

4. .idea/
--------------------------------------------------------------------------------
- Purpose:
  Integrated Development Environment (IDE) project configuration directory generated
  by JetBrains IDEs (PyCharm).
- Contents:
  Stores project-specific settings, interpreter associations, and code inspection profiles.

5. __pycache__/ (present in each package directory)
--------------------------------------------------------------------------------
- Purpose:
  Directories automatically created by the Python interpreter to store compiled
  bytecode (`.pyc` files) for imported modules, speeding up module loading.


================================================================================
10. INTER-COMPONENT DATA FLOW & WORKFLOW EXECUTION
================================================================================

1. Execution Flow:
   - When `pytest` is executed:
     1. `pytest.ini` is parsed: configuration options (`--alluredir=allure-results`,
        `--strict-markers`), asyncio settings, and marker definitions are loaded.
     2. `tests/conftest.py` initializes:
        - Evaluates CLI options (`--live` or `--mock`).
        - The `settings` fixture loads configuration from `config/settings.py` and `.env`.
        - The `mock_server` fixture automatically starts `MockAiravatServer` on
          `127.0.0.1:8008` if `USE_MOCK` is true.
     3. Pytest discovers and runs the test classes in `tests/suite_01_e2e_pipelines/`
        through `tests/suite_06_performance/`.
     4. During each test:
        - `AiravatApiClient` handles synchronous HTTP calls and logs Allure steps.
        - `AiravatAsyncClient` handles concurrent asynchronous calls.
        - `utils/file_generator.py` generates in-memory spreadsheet buffers.
        - `utils/assertions.py` validates precision, security headers, and sanitization.
        - `test_data/payloads.py` provides financial figures and attack strings.
     5. After test execution completes:
        - Teardown blocks in `conftest.py` delete created test models.
        - `mock_server` fixture cleanly shuts down the server socket.
        - Allure JSON files in `allure-results/` are ready for report generation.

2. Switching Environments:
   - To run against the built-in mock server:
     `pytest`  (or `pytest --mock`)
   - To run against the live backend (`https://10.20.11.244:3000`):
     `pytest --live`  (or set `AIRAVAT_USE_MOCK=false` in `.env`)
